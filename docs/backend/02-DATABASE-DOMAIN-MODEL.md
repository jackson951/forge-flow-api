# 02 — Database Domain Model

**Status:** NOT STARTED (see [00-BACKEND-ROADMAP.md](00-BACKEND-ROADMAP.md))

## Objective

Design and migrate the PostgreSQL schema that every later part relies on: identities, tenancy, workflow definitions and immutable versions, execution history, integrations and credentials, webhook deliveries and audit events — with the constraints and indexes that make isolation, immutability and idempotency enforceable by the database rather than by convention.

## Why This Part Exists

Most FlowForge guarantees are data guarantees: "a run describes exactly what executed", "a webhook cannot create two runs", "tokens never leak through a careless `include`". These are cheapest and most reliable when the schema makes the wrong thing impossible. Changing identifiers, ownership or version semantics later means data migrations across every table.

## Scope

- Prisma schema for all core entities and enums.
- Migration(s) that build the database from empty.
- Development-only seed (demo user + workspace, no real secrets).
- A decision record of modelling choices (below).

## Functional Requirements

| ID | Requirement |
| --- | --- |
| FR-02.1 | Every tenant-owned row is reachable to exactly one workspace through a non-null `workspaceId` (directly or via an immutable parent). |
| FR-02.2 | A workflow has one mutable draft and zero or more immutable published versions numbered 1..n without gaps. |
| FR-02.3 | A workflow run references the exact `WorkflowVersion` it executed; deleting or editing the draft never alters the run or its version. |
| FR-02.4 | A provider delivery (`provider`, `deliveryId`) can be stored at most once. |
| FR-02.5 | For any given trigger event and workflow, at most one run can be created (`workspaceId`, `idempotencyKey` unique). |
| FR-02.6 | Each run has at most one step record per node (`runId`, `nodeKey` unique); retries increment `attemptCount`. |
| FR-02.7 | Integration secrets live in a table separate from integration metadata. |
| FR-02.8 | Refresh tokens are stored hashed with rotation-family tracking. |

## Technical Requirements

### Entities

| Model | Purpose | Key constraints |
| --- | --- | --- |
| `User` | Identity | `email` unique (stored lower-cased), `passwordHash` never selected by default queries |
| `RefreshToken` | Session / refresh-token rotation | `tokenHash` unique; `familyId` indexed; `revokedAt`, `replacedById`, `expiresAt` |
| `Workspace` | Tenant | — |
| `WorkspaceMember` | Membership + role | unique (`workspaceId`, `userId`); index `userId` |
| `Workflow` | Mutable workflow + draft | index (`workspaceId`, `status`, `updatedAt`); `draftDefinition` JSON, `draftRevision` int (optimistic concurrency); `activeVersionId` nullable unique |
| `WorkflowVersion` | Immutable published snapshot | unique (`workflowId`, `version`); `definition` JSON, `definitionHash` (sha256), `schemaVersion`, `publishedAt`, `publishedById`; `workspaceId` denormalised for scoped queries |
| `WorkflowTrigger` | Routing index for active trigger subscriptions derived from the active version | index (`provider`, `eventType`, `externalResourceKey`); unique (`workflowId`) |
| `WorkflowRun` | One execution | unique (`workspaceId`, `idempotencyKey`); index (`workspaceId`, `status`, `createdAt`), (`workflowId`, `createdAt`); FK to version with `onDelete: Restrict`; `retryOfRunId` self-FK |
| `StepRun` | One node's execution within a run | unique (`runId`, `nodeKey`); index (`runId`, `sequence`) |
| `IntegrationConnection` | Connected external account (metadata only) | unique (`workspaceId`, `provider`, `externalAccountId`) |
| `IntegrationCredential` | Encrypted tokens for a connection (1:1) | unique `connectionId`; ciphertext columns only |
| `OAuthState` | Single-use OAuth `state`/PKCE verifier | `stateHash` unique, `expiresAt`, `consumedAt` |
| `WebhookDelivery` | Verified inbound provider delivery | unique (`provider`, `deliveryId`); `status`, `receivedAt`, `processedAt` |
| `AuditEvent` | Security-relevant actions | index (`workspaceId`, `createdAt`) |

### Common conventions

- UUID primary keys (`@db.Uuid`, generated by Prisma `uuid()`).
- `createdAt` on every table; `updatedAt` on every mutable table. Immutable tables (`WorkflowVersion`, `WebhookDelivery`, `AuditEvent`) deliberately have no `updatedAt`.
- Timestamps are `timestamptz` (`@db.Timestamptz(3)`).
- Enums for closed sets: `WorkspaceRole`, `WorkflowStatus` (`DRAFT`, `PUBLISHED`, `ARCHIVED`), `RunStatus`, `StepStatus`, `IntegrationProvider`, `ConnectionStatus`, `WebhookDeliveryStatus`, `TriggerSource` (`WEBHOOK`, `MANUAL`, `RETRY`), `ErrorCategory`.

### Deletion behaviour

| Parent → child | Behaviour | Reason |
| --- | --- | --- |
| Workspace → everything | Cascade | Deleting a tenant removes its data |
| User → WorkspaceMember, RefreshToken | Cascade | |
| User → WorkflowVersion.publishedBy, AuditEvent.actor | SetNull | History outlives accounts |
| Workflow → WorkflowVersion | Restrict while runs exist; workflows are archived, not hard-deleted, once they have runs (Part 05 policy) | Preserve run history |
| WorkflowVersion → WorkflowRun | Restrict | A run must always resolve its version |
| WorkflowRun → StepRun | Cascade | Steps have no meaning without the run |
| IntegrationConnection → IntegrationCredential | Cascade | |
| WebhookDelivery → WorkflowRun | SetNull on run's `webhookDeliveryId` | Delivery retention can be shorter than run history |

## API Changes

None. This part is schema-only.

## Database Changes

A new migration replaces the scaffold's `init` structure (the scaffold migration has only been applied to local development databases and has never shipped, so it can be reset rather than evolved). Changes versus the scaffold:

1. `Session` → `RefreshToken` with `familyId`, `replacedById`, unique `tokenHash`.
2. `WorkflowNode`/`WorkflowEdge` tables removed — see decision D1.
3. `WorkflowVersion` gains `definitionHash`, `schemaVersion`, `publishedById`, `workspaceId`.
4. `WorkflowStatus.ACTIVE` renamed `PUBLISHED`; `publishedVersionId` renamed `activeVersionId`.
5. `WorkflowRun.webhookEventId @unique` replaced by `idempotencyKey` unique per workspace + nullable `webhookDeliveryId` (one delivery may legitimately start runs for several workflows).
6. `StepRun` unique (`runId`, `nodeKey`), `attemptCount`, `errorCategory`, `sanitizedInput`/`sanitizedOutput`, `externalRef`.
7. Tokens moved from `IntegrationConnection` to `IntegrationCredential`.
8. `WebhookEvent` → `WebhookDelivery` with processing status.
9. New `WorkflowTrigger`, `OAuthState`.

## Security Requirements

- No plaintext passwords, refresh tokens, OAuth tokens or OAuth state values in any column — only hashes or AES-GCM ciphertext.
- Credential ciphertext lives only in `IntegrationCredential`, so default `include`/`select` of a connection cannot leak it.
- Seed data uses obviously fake values and runs only when `NODE_ENV !== 'production'`.

## Testing Requirements

- Integration test (real Postgres): `prisma migrate reset --force` on an empty database succeeds.
- Constraint tests: duplicate `(provider, deliveryId)` rejected; duplicate `(workspaceId, idempotencyKey)` rejected; duplicate `(runId, nodeKey)` rejected; deleting a `WorkflowVersion` with runs fails; deleting a workspace cascades.
- Index presence verified by querying `pg_indexes` for the required indexes.

## Risks / Design Questions

**D1 — JSON snapshot instead of normalised node/edge tables.** A published version is read and executed as a whole graph, never queried node-by-node. Storing the snapshot as one JSON document (plus `definitionHash`) makes immutability atomic and trivially verifiable, avoids reconstructing the graph with joins, and avoids two sources of truth (the scaffold had both `definition` JSON and `WorkflowNode`/`WorkflowEdge` rows). The cost is weaker database-level typing of the graph; this is mitigated by zod validation on write (Part 05) and a `schemaVersion` field for future format migrations.

**D2 — Immutability enforcement.** Prisma cannot declare a table append-only. Enforcement is: no update code path for versions in services, and a PostgreSQL trigger that raises on `UPDATE` of `WorkflowVersion.definition`/`definitionHash`, added as raw SQL in the migration. Tests prove both.

**D3 — `WorkflowTrigger` routing table.** Webhook intake must find subscribed workflows quickly without scanning JSON. The table is rewritten on publish/archive in the same transaction as the version change.

**D4 — Isolation via service-layer scoping, not composite foreign keys.** Composite FKs (`(id, workspaceId)`) would prevent cross-workspace references at the DB level but complicate every Prisma relation. Decision: scope every query by `workspaceId` in services, prove it with tests (Part 04), and revisit RLS or composite FKs in Part 22.

**D5 — One `StepRun` per node per run.** Retries of the same node update `attemptCount` rather than creating rows. A manual retry creates a new `WorkflowRun` (with `retryOfRunId`), so history stays readable.
